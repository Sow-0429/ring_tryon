# ADR-0001: Go/Python のサービス責務分割

- ステータス: Accepted
- 日付: 2026-05-30
- 関連: ADR-0003, ADR-0004

## コンテキスト

ring_tryon は「指号数計測 / リアルタイム指輪試着 / 試着画像生成」をAIで行う。
バックエンドには 2 つの異質な関心事がある。

1. 画像処理・数値計算（OpenCV/MediaPipe によるCV、px→mm スケール校正、楕円近似での
   周囲長算出、将来の回帰モデル）。Python エコシステムが圧倒的に強い。
2. ドメインモデル・業務ルール（号数マッピング、永続化、課金判定）。型安全と長期保守性が
   効くため Go の DDD レイヤで表現したい。

これらを 1 言語に寄せると、CV ライブラリの弱い側に無理が出るか、ドメインロジックが
スクリプト的に散らばる。

## 決定

サービスを 2 つに分割する。

- **Python (`ai_service`)** = 計算バックエンド。CV・セグメンテーション・スケール校正・
  楕円近似での周囲長算出・（将来の）回帰など、すべての数値計算を担う。出力は
  `circumference_mm` と信頼度入力を含む DTO（JSON/gRPC）。**号数は返さない。**
- **Go (`internal/`)** = DDD のドメインモデル（値オブジェクト・エンティティ・集約）、
  号数マッピング（`RingSize`、唯一の真実の源）、永続化（PostgreSQL）、課金判定。

Python 側の `Scale` / `DetectedCard` / `DetectedCoin` などは計算用の内部表現（DTO的）で
あり、DDD の正準型は Go 側に置く。

## 根拠

- 号数テーブル（JP 規格）が Go(`internal/ring_size`) と Python(`measurement.py` の
  `RingSize`) で重複しており、二重管理がバグの温床になっている。周囲長→号数の変換を
  Go に一本化することで「唯一の真実の源」を確立できる。
- CV/ML の進化は Python 側に閉じ込め、ビジネスルールの安定性は Go 側で守る、という
  変更頻度の異なる関心事の分離。

## 影響

- Python の `RingSize`（号数変換ロジック）は段階的に Go へ移譲し、Python は
  `circumference_mm`＋信頼度の算出までに責務を縮小する（移行は着手時に確定）。
- サービス間境界の DTO スキーマ（JSON/gRPC）を定義・バージョン管理する必要がある。
- ローカル開発・CI では 2 サービスを協調起動する構成が必要。

## 代替案と却下理由

- **全部 Python**: 号数・永続化・課金まで Python に置く案。型安全性とドメイン表現力で
  劣り、長期保守でルールが散逸するため却下。
- **全部 Go**: Go の CV/ML エコシステムが貧弱で、MediaPipe 等の資産を活かせないため却下。
